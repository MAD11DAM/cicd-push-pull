# Исследование моделей Push и Pull в CI/CD

**Дисциплина:** Киберриск и киберразведка  
**Тема:** Исследовать модели Push и Pull в CI/CD

## Цель
Сравнить способы доставки изменений и развёртывания приложений в CI/CD, показать их преимущества, ограничения и практические примеры.

## Что такое CI/CD
**CI (Continuous Integration)** — автоматическая проверка изменений при объединении кода. **CD (Continuous Delivery/Deployment)** — подготовка или автоматическое развёртывание проверенной версии приложения.

## Push-модель
После успешных тестов CI/CD-пайплайн **сам инициирует доставку** приложения в целевую среду, например с помощью SSH, API или команды деплоя.

Схема: `Git push → GitLab CI → тесты → команда развёртывания → сервер`.

**Плюсы:** простая централизованная настройка, быстрый запуск, понятный контроль из пайплайна.  
**Минусы:** CI-системе может потребоваться доступ к целевой среде и секреты для подключения; сложнее управлять большим числом окружений.

## Pull-модель
Агент внутри целевой среды **сам периодически проверяет** репозиторий или реестр и забирает одобренную версию или конфигурацию.

Схема: `Git push → GitLab CI → публикация артефакта/манифеста → агент в среде → получение обновления`.

**Плюсы:** целевая среда не обязана принимать входящие соединения от CI, доступы можно держать внутри среды, удобно для GitOps.  
**Минусы:** нужна настройка агента и мониторинга, обновление зависит от интервала проверки, возможна задержка.

## Сравнение

| Критерий | Push | Pull |
|---|---|---|
| Кто инициирует развёртывание | CI/CD-пайплайн | Агент целевой среды |
| Подключение к серверу | Обычно из CI к серверу | Обычно из среды к источнику |
| Контроль версии | Команда пайплайна | Желаемое состояние/версия в источнике |
| Примеры | GitLab CI + SSH, API деплоя | Argo CD, Flux |
| Основной риск | Секреты и доступы в CI | Компрометация агента или источника |

## Практическая часть
В этом учебном проекте GitLab CI выполняет тесты и **имитирует** два сценария без реального сервера:

1. `test` проверяет программу на Python.
2. `push_demo` запускает скрипт, который демонстрирует отправку версии из CI.
3. `pull_demo` запускает скрипт, который демонстрирует проверку версии агентом.

**Важно:** оба сценария — симуляции, а не настоящий деплой. Для полноценной Pull-модели нужен отдельный агент, работающий в целевой среде; здесь его поведение только показано скриптом.

## Как запустить в GitLab
1. Создать **публичный** проект `cicd-push-pull` на https://gitlab.com/.
2. Загрузить содержимое этого проекта в корень репозитория (включая `.gitlab-ci.yml`).
3. Открыть **Build → Pipelines** и дождаться выполнения пайплайна на доступном GitLab Runner.
4. Открыть логи заданий `test`, `push_demo`, `pull_demo`.
5. Отправить преподавателю публичную ссылку на репозиторий GitLab через Platonus до 9 ноября 2026 года.

## Вывод
Push-модель удобна для прямого управления развёртыванием из CI/CD. Pull-модель удобна там, где целевая среда самостоятельно применяет желаемое состояние. Выбор зависит от требований безопасности, сети и инфраструктуры.
